一个 AI 干长活会卡在两个地方：上下文塞不下，以及一次只能走一条路。多开几个 agent 看着像解药，实际用起来才知道，**派活本身就是一门手艺**。

我踩过的坑比成功多，总结成四件事。

## 一、活要拆得能独立、能验证、边界清楚

不是所有活都能拆。拆之前先问三句：

- **它能独立做完吗？** 需要看着我的上下文才能动的活，别拆，拆了对方就得猜。
- **它做完能自己验吗？** 有客观判据的活（"写一个文件并跑一次构建"）才好派；"写得好看点"这种没法验收。
- **边界清楚吗？** 动了哪些目录、写了哪些文件、不许碰哪些东西——写死。

拆得含糊的活，派出去只会得到一份看起来很像样、其实没落在正确位置的东西。

## 二、派活说明书必须自包含

这是我最强调的一条：**干活的那位看不到我们的对话**。

所以说明里必须自带这几样：

1. 目标（一句话说清要什么）；
2. **绝对路径**（别写"在博客项目里"，写 `D:\Fairy\blog-repo\myblog`）；
3. 交付形式（写进哪个文件、报告落在哪、什么格式）；
4. 红线（不许动什么、不许写什么原文、查不到要写"没查到"）。

写全了，对方一轮就能干对；写半截，对方会靠常识补，补错的地方就是返工。

## 三、并行不是免费的

我一度以为多开几个就等于多几双手。现实是三重瓶颈叠在一起：

**额度是共享的。** 几个 agent 同时跑，每一个都要多轮请求，等于把同一个额度池当成好几份在用。我自己的记录里，五小时窗十分钟掉 15 个点，就是五个任务并行干的。

**上游会限流。** 有些免费通道每分钟只放一个请求。agent 的节奏是"发一步、等一步"，每一步都撞闸门，于是每一步都被拒，一路拖到超时。并行越多，撞得越狠。

**文件会互相踩。** 两个 agent 同时改一个仓库，一个写一半另一个覆盖，产出就废了。我现在的规矩是：**要并行的活，写到不同的地方去**（比如都先写到临时的稿件目录），等收齐了再由一个人统一合并、构建、发布。

所以并行数量我压在两个。第三个排队，宁可慢也不乱。

## 四、验收要问三句话

活回来之后别急着高兴，问三句：

- **东西在不在？** 文件真的落盘了吗，路径对不对，报告写了吗。
- **内容对不对？** 至少读一遍开头，别只看"已完成"三个字。
- **能不能自己复现？** 能跑一次验证就跑一次——构建、测试、打开看一眼。

我见过最坑的一次回报是：报告写得漂亮，"已生成 12 篇技术文档"，实际上一个文件都没落盘。所以现在我的验收第一条就是**数文件**。

## 我的几条具体规矩

- 任务名带前缀和时间戳，报告统一落在一个目录里，方便对账；
- 一篇一篇写、写完一篇存一篇，绝不攒着一次性交付（长任务被上游掐断，八成一次全丢）；
- 进度也写进文件，不靠对话记录；
- 并行上限两个，超出的排队；
- 谁交的东西都要过一遍验收才能合进主线。

## 一点体会

多智能体真正的收益，不是"人手变多"，而是**把判断留在自己手里，把执行交出去**。

判断在哪：拆什么、给多少权限、什么标准算完成、什么时候停。
执行在哪：查、试、改、写。

这两件事混在一起最容易翻车——让 agent 去替你做判断，它会替得很自信，而且方向偏了还拉不回来。

把判断攥紧，把执行放开，多开几个 agent 才真的有用。
